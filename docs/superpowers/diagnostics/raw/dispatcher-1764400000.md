## 4. 结论与判定

### 判定结果：**A —— 平台/配置问题**

判定依据（按优先级）：

1. **最直接的事实**：本会话系统提示注入的 `<mcp_file_system_servers>` 清单只列出一个 server —— `integrated_code_mode`。6 次 `run_mcp` 探测（包含 `agent-flow-ex` / `mcp_agent-flow-ex` / `agent_flow` / `agentflow` / `agent-flow-ex-b1bcbfb1` / `connector-proxy`）全部返回 `MCP server is not found`。**这是底层调度层在加载 MCP server 时找不到目标 server，而不是 server 已加载但工具调用失败。**
2. **注册表层级证据**：`/Users/meow/.trae-cn/mcps/` 下虽然存在 `s_agent-flow-ex-b1bcbfb1/...` 物理目录，但其 SERVER_METADATA.json 暴露的 server_name 是 `integrated_code_mode`。本机注册表里**真实注册**的 server 只有 `integrated_code_mode` 和 `integrated_browser` 两个。
3. **配置层级证据**：`~/.workbuddy/.mcp.json` 引用了 `connector-proxy (http://127.0.0.1:62415/mcp)` 并声称其聚合 `agent-flow-ex, agent-mail`，但 `connector-proxy` 这个 server **既不在注册表里，也不在本会话可用清单里**——配置和实际注册脱节。

**结论**：「agent_flow_* 工具不可见」的根因是 **`agent-flow-ex` 这个 MCP server 没有作为独立的 server 被注册到本会话可访问的注册表**。修复路径属于 A 类，需要：
- 确认 `~/.workbuddy/.mcp.json` 引用的 `connector-proxy` (127.0.0.1:62415) 在 Schedule 触发时是否实际运行；
- 若 proxy 不可用或 agent-flow-ex 缺失，应在 WorkBuddy/TRAE SOLO CN 的 MCP 配置面板里把 `agent-flow-ex` 注册为一个独立可加载的 MCP server（而不是仅作为聚合 proxy 的描述字段）。

### 不属于 B / C 的理由
- **B 不成立**：B 要求「MCP server 已在注册表里但 Schedule 会话加载不到」。本机注册表里**根本没有**名为 `agent-flow-ex` 的注册条目，所以不是「注册了但没加载」，而是「根本未注册」。
- **C 不成立**：C 要求「agent_flow_* 工具可见但调用报错」。本会话连工具都不可见，调用失败的错误是 `MCP server is not found`（注册层失败），而非 server 启动后工具执行的运行时错误。
