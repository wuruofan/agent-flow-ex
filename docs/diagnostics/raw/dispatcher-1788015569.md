## 5. 结论（重新判定）

### **判定：B. MCP server 启动成功但工具没出现在 Schedule 会话的工具列表 → Trae Schedule 会话没加载 MCP**

证据链：
1. **注册正确**：`User/mcp.json` 明确写了 `agent-flow-ex` → `node /Users/meow/workspace/agent-flow-ex/dist/server.js`。
2. **配置路径全部有效**：`node` 二进制 + `dist/server.js` 双方都存在、可执行。手动 stdin 触发 `initialize` 立即返回合规的 MCP 握手，`serverInfo.name="agent-flow-ex"`。
3. **平台侧确认拉起**：render.log 在 08-27 21:42 留下 `McpClientService startExtension: mcp.config.usrlocalmcp.agent-flow-ex {…}`，与 mcp.json 命令字字相同。
4. **业务工具在主会话内一直工作**：08-29 上午 7 次 `agent_flow_submit` / 多次 `agent_flow_status` / 2 次 `agent_flow_cancel` 全部 `code:0`，覆盖 queued → running → needs_input → completed 完整状态机，task_id 真实持久化。
5. **但 Schedule 会话工具列表里没有 `agent_flow_*`**：本会话系统提示的 `<mcp_file_system_servers>` 只注入 `integrated_code_mode`。对 `agent-flow-ex` / `mcp__agent-flow-ex` / `mcp_agent-flow-ex` 任何 server 名的 `run_mcp` 调用都从未实际发生——因为本会话工具集里就没有这一族可调用入口。
6. **错误时间分布佐证**：08-29 15:11、22:51 的 render 日志显示「Extension mcp__agent-flow-ex not found」、「Extension agent-flow-ex not found」、「Tool agent_flow_status not found in mcp server」，都出现在 Schedule chatSession 上；主会话的同期/更早调用反而全部成功。这强烈指向 **「主 IDE 注入 MCP 的机制 vs Schedule 子会话注入 MCP 的机制不是同一条路径」**——后者在配置刷新或重启窗口后丢了「agent-flow-ex → 当前 server 标识符」映射。

### A / C 不成立的依据
- **A 不成立**：配置路径全部有效，注册项就位；server 手动启动 0 错误，stdio/MCP 协议层正常。
- **C 不成立**：08-29 上午主会话下 `agent_flow_*` 调得通且拿到正确响应；之后即便失败，也不是 server 自身崩了，而是 Schedule 子会话**根本拿不到**这一族工具的定义（错误是 `Extension … not found`，不是 `tool execution error`）。

### 次要观察（不影响主判定）
- 日志里出现参数类型校验错误（`Expected string, received number at prompt` 11:41 / `Expected number, received string at timeout_sec` 11:43）是上游 LLM 调用方把参数类型写错（worker 调用 MCP 时的 protocol 类型错误），与本机注册/启动无关。
- `updatePluginMcpConfigs` 在所有样本里都报告 `globalCount:0, projectCount:0, serverNames:[]`——这说明 [PluginMcp] 通道的 mcp 配置视图里一直是空，但走 [McpClientService]/[McpService] 的 usrlocalmcp 通道里 agent-flow-ex 是有效的。两条通路不一致是本机 Trae 的现状。
