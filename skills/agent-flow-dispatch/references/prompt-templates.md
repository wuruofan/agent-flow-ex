# Prompt 模板

worker（后台 agent CLI）不共享调度会话的任何上下文。以下模板保证工单自包含。填好后整体作为 `agent_flow_submit` 的 `prompt`。

## 模板 A：编码任务（功能/修复/重构）

````text
你是 <project_path> 项目的后台 worker，独立执行本工单，不向任何人提问、不依赖外部上下文。

## Mission
<一句话：要做什么>

## Context
- 项目路径：<绝对路径>
- 技术栈 / 构建命令：<如 Node 24 + TypeScript，npm run build / npm test>
- 关键文件（先读再改）：
  - <文件绝对路径> —— <为什么相关>
  - <文件绝对路径> —— <为什么相关>
- 现状事实：<当前行为/已知缺陷/最近相关改动，越具体越好>

## Constraints
- 只改动本工单范围，不碰：<无关模块/文件>
- 遵循：<该仓库规范，如 conventional commit、docs/ 目录约定>
- <其他约束>

## Acceptance Criteria（全部满足才算完成）
1. [ ] <可验证的标准 1>
2. [ ] <可验证的标准 2>
3. [ ] 现有测试通过（<命令>）

## Git Discipline
不要执行 git commit / push / rebase / stash 等任何写操作；只修改工作区文件。完成后输出：改了哪些文件、每个文件改了什么、验证结果。

**里程碑 commit 变体（仅当整个任务序列已作为 plan 预先批准时使用，替换上面的 Git Discipline）**：
```
## Git Discipline
每完成一个「实现 + 验收都通过」的里程碑就地 git commit（遵循仓库 commit 风格；不 push、不 rebase、不 stash）。
里程碑未过验收就不要 commit；被杀时未提交的工作按残留如实报告。
```

## Deliverables
以文字汇报：变更文件清单 + 摘要 + 测试/验证输出。不要创建 PR、不要发通知。
````

使用要点：
- **Context 里给足绝对路径与现状事实**——worker 看不到会话，宁可多写两行现状，不要让它去猜。
- 目标仓库若是公司项目/需要特定 commit 纪律，在 Constraints 里写清；但 Git Discipline 默认仍是不 commit。
- 任务若引用了 spec/plan 文档，把文档路径放进 Context（如 `docs/superpowers/plans/xxx.md`）并指示先读。
- **交付物的顺序 = 抗截断顺序**：`MAX_RESULT_LEN=4012` 截的是报告**尾部**（详见 `confidence-check.md` 第 1 条）。
  所以工单里要把**只有 worker 知道**的那几节排在最前——「做不到逐位相同」「偏离 plan」「没验哪一部分」
  「需调度方裁定」——把「改了哪些文件、命令输出贴了多少」放后面。判据：**那一节的内容我能不能自己从磁盘
  重跑出来？** 能（测试数字、tsc 计数、diff 清单）就抗截断，放后面无所谓；不能（worker 的判断、它放弃的
  路径、它自认的未验项）才必须靠报告，被截掉就等于没交。9/19 实测：我的工单把 §6/§7 排在 7 节之末，
  卡片截断后正好只丢这两节——而 §1–§5 全是可自己复跑的数字。用「§0 结论 + 遗留」开篇，
  并给报告**写明长度上限（1–2 KB）**；长报告必被腰斩。
- **时间预算不用写进工单**：runner 会自动把本任务 `timeout_sec` 注入 worker 行为契约（`src/prompt.ts`），worker 在预算用尽前（剩余 <15–20%）会自行把进度写进项目根目录 `HANDOFF.md`（**不 commit / 不 push**）。调度方收到 timeout 终态时**先看该文件**，据其判断残留与续做方式——这也让"未提交却已改到一半"的脏树自带说明。注意 HANDOFF 只帮 salvage，**不防丢代码**；防丢靠工单粒度 + 里程碑 commit（见 SKILL.md「工单粒度与预算」与上面的 Git Discipline 变体）。

## 模板 B：needs_input 续跑答复

````text
<针对 worker 提问的直接答案，把可选项/决策一次性说清>

背景补充（如需要）：<只补本次答复需要的新事实，不要重复整份工单>
```

提交为 `agent_flow_submit({ continue_of: <task_id>, prompt: <上面内容> })`。worker 带着原上下文继续，所以只答问题本身，简洁为要；但若你的答复引入了原工单没有的新约束，要把新约束写清楚。

## 模板 C：只读评审/调研（不改代码）

````text
你是 <project_path> 项目的后台 worker，做只读分析，不修改任何文件。

## Mission
<评审/调研目标，如：审阅 docs/designs/xxx.md 对照 src/ 现状>

## Scope
- 只读：禁止修改/新建文件。
- 依据证据（文件、代码、日志）下结论，不臆测；结论标注局限。

## 输出格式
按 P0/P1 分级问题表：问题 | 证据（文件:行号/引用）| 建议修复。最后给结论摘要。
````

## 提交前自查清单

- [ ] prompt 里出现了目标项目绝对路径（或 project_path 已显式传）？
- [ ] 没有依赖"调度会话里说过的话"？关键事实都已写进 prompt？
- [ ] 同 `project_path` 没有并发任务？
- [ ] Git Discipline 已按用户意图写明（默认不 commit/push）？
- [ ] 未包含任何密钥/token/私密信息？

## 派发前自检字段化（来自 SKILL.md Step 2）

模板 A 的 Context 字段下方加一个 `## Context（调度方已确证事实，直接作为输入）` 小节，把 SKILL.md 的 6 项自检清单落到 prompt：

| 自检项 | 落点（写到 Context 的哪一行） |
|---|---|
| 1. 项目路径 + 技术栈 + 构建命令 | 第一行 + 第二行 |
| 2. 必读文档绝对路径 | "关键文件" 列表 |
| 3. 已跑过的命令与结果 | "调度方已确证" 段，每条标注来源（"调度方已 grep / 前序 task_xxx result 第 §Y 节 / 8-26 文档 §X.Y"） |
| 4. 已 grep / 已 cat 过的嫌疑代码行号 | "关键文件" 列表的 `<为什么相关>` 字段，附 `:行号` |
| 5. 已知失败模式 / 排除路径 | "Constraints" 前加 `## 已知失败模式` 小节 |
| 6. 环境陷阱 | "Constraints" 段加一行说明（如"机器有双 bun，默认用 1.4.0；用户预存在 bun run dev PID 66820/66821 保留勿动"） |

## 好 prompt 演化样本

来自 9/3 的 motelet stall 调查系列（task_mtla69fx_3872f3 → task_mtljliko_759d7a → task_mtlm3cw0_77f477），prompt 字数从 2642 涨到 4347，但 worker 跑得更高效、不需要重复排查。关键模式：

- **"调度方已确证事实，直接作为输入，勿重新质疑"**——给 worker 划清"信任边界"，避免它在已有结论上重新调查。
- **"按信息量排序的定位思路"**——列 3-4 条候选路径并标注信息量与预期主路径，让 worker 选最有希望的。
- **"前序已做 X（如『已跑 4 轮 sample』），不要重复全量"**——明示已完成的步骤，让 worker 接力而非重启。
- **"防假阳性守则：必须见 Ran 行才算通过"**——把"什么算成功"明确化，不靠 worker 自行判断。
- **"若需三处修复之外的改动才能完成，停下汇报，不要擅自动"**——给 worker 授权"卡住就停下走 needs_input"，避免越界。

反面例子：完全空白让 worker 从零开始（占 worker token 探索，但占调度方极少），适合一次性、非关键、不紧急的小任务；不适合长期项目的事务型派活（占 worker 多但占调度方更多）。
